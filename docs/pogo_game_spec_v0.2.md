# ポゴ系 面クリアアクション 仕様書 v0.2

- エンジン: Godot 4.x / PCスタンドアロン（Windows想定）
- ジャンル: 物理跳躍アクション（面クリア型）
- 判定: 2D（横視点）
- 表示: ステージ画像（ビットマップ）＋ ポリゴンコリジョン

---

## 1. コアループ

```
面に入る → 跳んで登る → 落ちる（軽い復帰）→ 収集アイテムを取る
→ ゴール → スキル解放 → 前の面の届かなかった場所に戻れる
```

「落下ペナルティが軽い」ため、難度の主軸は **恐怖 → 精度と反復** に移る。
その分、収集アイテムを危険な位置に置くことで緊張を作る。

## 2. プレイヤー操作

### 入力（キーボード基準／パッドも同マッピングで対応）

| 入力 | 動作 |
|---|---|
| ← / → | ポゴの傾き角θを左右に回す（角速度制御） |
| Space（保持） | チャージ。離すか着地でリリース |
| R | 手動リトライ（直近チェック地点） |
| Esc | ポーズ／スキルツリー |

### 傾き制御
- θ は目標角ではなく**角速度で回す**。`θ += tilt_input * TILT_SPEED * dt`
- キーを離すと `STABILIZE_RATE` で 0° に戻る（安定性スキルで上昇）
- 可動域: ±60°（初期）

### 反発（接地の瞬間のみ発生）
```
n      = 接触面の法線
v_in   = 接触直前の速度
base   = reflect(v_in, n) * RESTITUTION
dir    = θ から作った射出方向ベクトル
v_out  = lerp(base, dir * |base|, POGO_AUTHORITY) + n * BOUNCE_ADD
```
- `POGO_AUTHORITY = 0.75`（プレイヤー意志が7.5割、地形反射が2.5割）
- `BOUNCE_ADD` は最低跳躍量。これがないと平地で死ぬ

### チャージ
- 接地の**前**に押していれば有効（先行入力を許可）
- 蓄積 0〜1.0（満タン 0.6秒）→ `BOUNCE_ADD` と `RESTITUTION` を最大 1.5倍
- 満タン時のみ画面端に微発光（音でも通知）

### 転倒（ダウン） — 廃止
- v0.3 でこの判定自体を削除。着地はθに関わらず常にバウンドする
- 理由: 転倒→復帰待ちが操作感を損なうためゲームとして不要と判断

## 3. ストレス低減補正

| 補正 | 内容 |
|---|---|
| 入力バッファ | 接地の8フレーム前までの入力を接地時に適用 |
| 着地スナップ | 目標角との差が±5°以内なら自動吸着 |
| エッジアシスト | 縁を6px以内で掠めた場合、接地扱いに寄せる |
| 壁反発減衰 | 壁面（法線が水平寄り）は反発0.4倍。無限バウンド事故を防止 |
| 天井処理 | 天井接触は反発せず速度を殺すのみ |
| カメラ先読み | 上昇中はデッドゾーンを下げ、上方を多く映す |
| コヨーテ角 | 接地判定と同時にθを1フレーム保持し、判定の揺れを吸収 |

## 4. 落下と復帰

「落下地点付近に即復帰」を採用。ただし完全無痛にはしない。

- ステージには **リカバリーポイント**（不可視、地形上に自動配置または手置き）を持つ
- 落下判定 = 「連続下降距離 > FALL_THRESHOLD（初期900px）」かつ着地
- 復帰先: 落下開始地点から**下に1段だけ**戻ったリカバリーポイント
- 復帰演出 0.5秒（フェード＋SE）。これが実質的なペナルティ
- 落下カウンタを面ごとに記録（スコア表示用、成長要素には非連動）

### リトライスキル
- 「リトライ」系スキルは **チェックポイント設置権**：
  - Lv1: 面内に任意で1回セーブ地点を打てる
  - Lv2: 2回
  - Lv3: 復帰演出短縮（0.5s → 0.15s）
- 落下復帰が軽い設計なので、リトライスキルは「登り直しの手間削減」に振る

## 5. スキルツリー

### ポイント入手
**ステージ内の収集アイテム（Cog）のみ**。
- 1面あたり 4〜6個
- 配置ルール:
  - 1〜2個: 通常ルート上（誰でも取れる）
  - 2〜3個: 現在のスキルでは届かない位置（再訪前提）
  - 1個: 明確に危険な位置（落下確定ルートの先端）
- 取得は永続。落下しても取得済みは維持

### ツリー構成（低コスト多段・分岐なし推奨）

| 系統 | Lv1 | Lv2 | Lv3 |
|---|---|---|---|
| ジャンプ力 | BOUNCE_ADD +8% | +16% | +25% |
| 安定性 | 復元速度 +30% | +60% | 可動域 ±75° |
| スーパージャンプ | 満タンチャージで1.8倍（CT 6秒） | CT 3秒 | 空中で1回だけ発動可 |
| リトライ | チェック地点1回 | 2回 | 復帰演出短縮 |

コストは 2 / 3 / 5 Cog。全解放に約 40 Cog ＝ 8面分。

## 6. ステージ

- 1面サイズ: 3840 x 2160（1080p換算で2x2画面）
- 面数: 初期リリース 8面（+ チュートリアル1）
- 目標クリア時間: 初見 3〜6分 / 熟練 40秒〜

### シーン構成
```
Stage.tscn
├── ParallaxBackground/  (Sprite2D 背景レイヤー ×2)
├── StageArt             (Sprite2D  地形の見た目)
├── Terrain (StaticBody2D)
│   └── CollisionPolygon2D × N   ← 見た目とは別データ
├── RecoveryPoints (Node2D)      ← Marker2D × N
├── Collectibles   (Node2D)      ← Cog.tscn × 4〜6
├── Goal (Area2D)
└── StageBounds (Area2D)         ← 場外落下の保険
```

### コリジョン制作パイプライン
1. ステージ画像を作る（PNG, 3840x2160）
2. 外部ツールでポリゴン輪郭を作成（Blender / Inkscape / 自作エディタ）
3. 頂点配列を JSON でエクスポート
4. Godot 側 `@tool` スクリプトで `CollisionPolygon2D` を生成
   - 1ポリゴンあたり頂点は 200 以下に分割
   - 凹形状は Godot が自動で凸分割するが、極端な形状は手動分割
5. デバッグ表示（F1でコリジョンのみ表示）を必ず用意

## 7. データ設計（Godot Resource）

```gdscript
# PogoStats.tres  — 物理パラメータの実体
class_name PogoStats extends Resource
@export var restitution      := 0.62
@export var bounce_add       := 380.0   # px/s
@export var pogo_authority   := 0.75
@export var tilt_speed       := 180.0   # deg/s
@export var stabilize_rate   := 120.0   # deg/s
@export var tilt_limit       := 60.0    # deg
@export var gravity          := 1800.0
@export var charge_time      := 0.6
@export var charge_mult      := 1.5

# SkillData.tres — 1スキルの定義
class_name SkillData extends Resource
@export var id: StringName

```

## 10. レベルデザイン指針（実装で確定した運用ルール）

§6のステージ仕様は初期案（1面 3840×2160 固定）だったが、実装では**ステージごとに可変の `camera_bounds`** を使う方式に変わっている。以下は実装を通じて固まった、面を作る上での実務ルール。

### camera_bounds の意味と落とし穴

`Stage.camera_bounds`（Rect2）は**カメラの可動範囲**と**落下死の判定線**を1つの値で兼ねる。

- `position.y`（上端）＝そのステージで登れる一番高い場所
- `position.y + size.y`（下端）＝落下死の基準線
- Rect2なので、**上端だけ広げたいときに`position.y`だけ動かすと下端も一緒に動く**（`size.y`も合わせて増やすこと）。これをやると「開始した瞬間に落下死する」という原因の追いにくい事故になる
- 落下死の実判定線は `下端 + fall_margin`（既定400px）。強いバウンドで大きく跳ねても誤判定しないための余裕
- 読み込み時に自動チェックが走り、①開始位置/復帰地点が死の線より下、②地形が`camera_bounds`（+64pxの余裕）からはみ出している、の2点を警告する。地形を作ったら必ず`camera_bounds`のサイズも合わせて調整すること
- 縦幅は最大 **size.y ≒ 6000px** 程度まで動作確認済み（背景の縦方向parallaxを画面固定にすることで、ステージがどれだけ縦長でも背景に穴が出ない設計にしてある）

### 背景（BG）の運用ルール

- Sky / Far / Mid / Near の4層構成（`Background.tscn`）。奥から順に空・遠景・中景・近景
- **縦方向のparallaxは全レイヤー`1.0`固定**（画面に完全に張り付く）。ステージの縦幅に関係なくBGが途切れないための必須設定
- 横方向のparallaxはレイヤーごとに変えて奥行き感を出す（Sky 0.03 〜 Near 0.55）
- 新規BG画像を作るときは **480×378px** を基準解像度にする（ドット感を保つための取り決め。詳細は`bg_layer.gd`/`terrain_sprite.gd`のコメント参照）

### 地形タイルの解像度指針（ドット感）

- 表示は常にニアレストネイバー。**画面上の1ドット ≒ 4px** を目安に、タイル画像の解像度を決める
- 目安の計算式: `タイル画像の幅 = 画面上の表示幅 ÷ 4`（画面上の表示幅はタイルサイズ×カメラzoom 1.4で決まる）
- 足場グラフィックには自動で輪郭線と下端の影が付く（`TerrainSprite`の`outline_*`/`shadow_*`パラメータで調整可能）

### BGMの割り当て

- ステージ1曲を直接指定する方式（`Game.stage_bgm`配列）。曲数を割り算で自動配分する方式ではなく、面ごとに手動で割り当てる
- 現状は3曲（BGM01〜03）を10ステージへ配分済み

## 11. コア体験とステージテーマ（数値分析に基づく設計指針）

### 11.1 現在のパラメータが定める「できること／できないこと」

`pogo_stats_default.tres`の実測値ベース。

| 数値 | 設計への含意 |
|---|---|
| tilt_limit 35° / tilt_speed 30°/秒 | 左右の反転に2.3秒かかる |
| air_control 20 | 滞空1秒で±10px。空中の軌道修正はほぼ効かない |
| gravity 450（初期値の1/4） | 滞空が長い。傾きを合わせる時間は十分ある |
| restitution 0.18 + pogo_authority 0.93 | 斜面で弾き飛ばされない。角度は地形ではなく自分で作る |
| charge_hold_time 0.25秒 | その場に留まれない。「安全に考える場所」が作れない |
| ground_normal_threshold -0.85 | 約32°より急な面は壁扱い。緩斜面しか足場にならない |

つまりこのゲームの中核は**「先を読んで、長い滞空の間に角度を作り込み、あとは委ねる」**。マリオのような瞬間的な操作ではなく、事前コミット型の照準に近い。

**全ステージはこの一点を教え、変奏するべき。** 逆に「空中で慌てて立て直す」設計は、数値上できないので作っても機能しない。

### 11.2 10ステージのテーマ案

マクロで起承転結を割り、各ステージ内でも4段階（導入→発展→ひねり→収束）を回す構成。**各ステージで新要素は1つだけ**にするのが要点（3で天井、6で壁、というようにその回で覚えることを絞る）。

| # | 題材 | 段階 | 教える／試すこと | 地形の見立て |
|---|---|---|---|---|
| 1 | ビール | 起 | 跳ねるのは自動。傾きが進む方向を決める | ほぼ平地。段差だけ |
| 2 | たこ焼き | 起 | 1バウンドで進める距離の感覚 | 丸い足場を等間隔に。下に受け皿の床 |
| 3 | ハイボール | 承 | チャージで高く跳ぶ | グラスの中を登る縦長。天井で跳びすぎを罰する |
| 4 | 櫛羅 | 承 | 2.3秒かかる方向転換を事前に仕込む | 一合瓶の細長い縦。転換点は1回だけ |
| 5 | お好み焼き | 承 | 緩急。ここまでの技を自由に使わせる | 広い円形の鉄板。複数ルート |
| 6 | 風の森 | 転 | 壁（32°超）に触れると0.39倍に減速して落ちる | 泡が昇る縦の隘路。壁が交互に迫る |
| 7 | ラーメン | 転 | 「止まれない」こと自体が課題 | 麺＝細い足場の連続。リズムが途中で変わる |
| 8 | ALPHA | 転 | 全要素を狭い許容誤差で。チャージ量を"ちょうど"に | 最も精密 |
| 9 | パフェ | 転（頂点） | 総合。縦に積み上げて登り切る | パフェのグラス。最上段が狭い |
| 10 | 大扉 | 結 | 難易度を落とし、演出で締める | 門へ一直線。ゴール判定が大きい（239x358） |

### 11.3 優先で直すべき点：復帰地点の設置状況

復帰（チェックポイント）システム自体は実装済み（`Stage`に`RecoveryPoints`（Marker2D）を置くと、通過時に記録され、落下時はそこへ戻る。§10の表とは別に現状を確認したところ、**精密系ステージほど未設置**という食い違いがあった:

| ステージ | 復帰地点の設置数 |
|---|---|
| 1, 3, 4, 5, 6 | 3箇所ずつ設置済み |
| 2 | コンテナのみ存在、中身は空（0箇所） |
| 7, 8, 9, 10 | `RecoveryPoints`ノード自体が無い（0箇所） |

§11.2で7〜10を「転」の精密系に据えるなら、この4面（と2）への復帰地点設置は他のどの作業よりも優先度が高い。Stage09は§10の通りまだ未着手（Stage01の複製）なので、テーマ差し替えと同時に対応すること。
